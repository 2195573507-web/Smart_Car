# YDLIDAR S3-ROS2-STM32 构建与审计计划

## 1. 文档状态

| 项目 | 值 |
| --- | --- |
| 状态 | 待批准的实施与审计计划 |
| 目标 | 建立 `YDLIDAR -> ESP32-S3 -> Wi-Fi -> Windows ROS2` 的可审计雷达数据上行链路 |
| 当前范围 | 雷达数据采集、校验、网络上行、`/scan`、时间/状态诊断与三端安全边界 |
| 明确排除 | 本轮不把雷达原始数据发给 STM32；不启用 Nav2 对车体的运动控制；不改 GPIO4 PWM 策略；不把 ROS2 DDS 暴露到跨 Wi-Fi 网络 |
| 代码实施前置 | 本计划获得批准，且 P0 的接口、网络和安全准入项通过 |

本计划是实施顺序与审计合同，不代表 Wi-Fi、ROS2、雷达解析、STM32 链路或车辆运动已经验证成功。

## 2. 已确认基线与待确认项

### 2.1 已确认的源码事实

| 域 | 当前事实 | 审计含义 |
| --- | --- | --- |
| 雷达输入 | S3 使用 UART1、GPIO44 RX、115200 8N1；雷达侧未接 S3 TX | Windows/ROS2 不得向此设备路径发送查询、启动或 DTR 命令 |
| 雷达 PWM | GPIO4、10 kHz；当前活动宏为 0% duty | 本计划不修改 PWM，所有实施阶段均须保持该文件的 PWM 宏不变 |
| 当前 S3 行为 | `radar_uart.c` 连续读取 UART 原始块并限流发 BLE 日志 | 当前已证明原始字节可接收，不证明包校验、点数据或扫描完整性 |
| 已存在解析器 | `radar_parser.c` 有环形缓冲、`AA 55` 定界和样本长度框架 | 它尚未列入 `main/CMakeLists.txt`，也未接入 UART 任务；不能称为已运行解析器 |
| S3-STM32 链路 | UART2 GPIO17/18、921600 8N1、SRPv4 已有独立协议 | 雷达上行不可挤占此链路，也不可重定义现有 SRPv4 帧 |
| STM32 安全 | CM7 在调度器启动前执行 `motor_board_force_stop()`，并由既有安全/姿态链路控制电机准入 | ROS2 未来只可提交受限运动意图；不得输出 PWM 或绕过 STM32 的停止门 |
| ROS2 主机 | `ROS2_WIN/` 尚无工作区或节点 | 所有 ROS2 构建、容器和运行证据均需从零建立并单独记录 |

### 2.2 必须在 P0 冻结的决策

| 决策 | 推荐值 | 未冻结时的风险 |
| --- | --- | --- |
| 近场网络 | Windows 热点或随车旅行路由器，使 S3 与笔记本处于同一 LAN | 跨 NAT 直接 TCP 和 DDS 发现不可复现 |
| 远程网络 | MQTT over TLS 或 WSS 公网中继；S3 与 ROS bridge 都主动出站连接 | 笔记本入站端口、动态公网 IP 和 NAT 会阻断连接 |
| 初版上行负载 | S3 校验后的完整 YDLIDAR 包，不传 S3 解算后的 `LaserScan` | 在 MCU 过早固化角度、时间和 ROS 语义，增加调试难度 |
| Windows 运行域 | Windows 上的 WSL2/Docker 内 Ubuntu 22.04 + ROS2 Humble；bridge、TF、SLAM 初期同一 Linux 域 | 原生 Windows、WSL2、Docker 与跨主机 DDS 同时排障，变量过多 |
| 雷达包模式 | 先以捕获数据确认 X3/X3 Pro、checksum 和样本字节数，再启用解码 | 强度/无强度模式或校验算法猜错会污染全部 `/scan` |
| 时间基准 | 网络包同时携带 S3 单调时间与序号；ROS bridge 初版采用主机接收时间，SLAM 前再验证 NTP/SNTP 偏差 | 将不可比的时钟直接作为 ROS 时间戳会破坏 TF/里程计对齐 |

## 3. 目标架构与不变量

```text
YDLIDAR X3/X3 Pro
  -> S3 UART1 RX / GPIO44
  -> S3 包定界、YDLIDAR CS 校验、计数与最新数据槽
  -> S3 Wi-Fi 上行协议（LAN TCP；远程 MQTT/TLS 或 WSS）
  -> Windows WSL2/Docker: s3_ydlidar_bridge
  -> sensor_msgs/msg/LaserScan: /scan
  -> TF + odom -> SLAM Toolbox -> Nav2

ROS2 高层运动意图（后续独立阶段）
  -> S3 控制仲裁
  -> 既有 SRPv4 / UART2
  -> STM32H757 最终限速、停止与执行安全
```

必须始终满足：

1. S3 是 YDLIDAR UART 的唯一拥有者；官方 ROS2 driver、PC 工具和 STM32 均不得并发打开或控制该设备。
2. `radar_uart`、Wi-Fi 上行、BLE 日志、S3-STM32 控制链使用有界且彼此隔离的缓冲；雷达拥塞只能丢弃旧数据，不能阻塞控制或无限积压。
3. 雷达流只上行到 ROS2。STM32 不接收原始雷达包、点云或扫描数据。
4. ROS2 网络断开、数据过期、解析错误或 TF 不完整时不得生成任何运动命令。紧急停止与最终执行安全仍在 S3/STM32。
5. 任何阶段的构建成功仅证明该域可编译/链接；无线、串口、雷达、时间同步和车辆行为必须用相应现场证据验收。

## 4. S3-ROS2 网关目标合同

### 4.1 数据包边界

初版发送单位是 **一帧已通过 YDLIDAR checksum 的原始扫描包**，而不是任意 UART `read` 块。拟议网关头部字段如下；具体字节布局须在 P1 设计审计中冻结后才可实现：

| 字段 | 用途 |
| --- | --- |
| magic、版本、消息类型 | 识别协议和拒绝不兼容数据 |
| device_id、stream_id | 允许主机拒绝错误设备/错误流 |
| sequence | 检测重复、乱序和丢包 |
| S3 单调时间戳 | 诊断 S3 接收和网络传输时延，不直接假定为 ROS 时间 |
| scan_epoch 或零位包标记 | 辅助 ROS bridge 判定一次完整旋转 |
| payload_length | 处理 TCP 分段/合并，限制解析内存 |
| payload | 完整 YDLIDAR 原始包，包含原协议 CS 字段 |
| 外层 CRC 或 TLS 完整性策略 | 防止自定义报文误拆；TCP 不替代应用定界 |

外层负载长度必须有明确上限，接收端在分配前验证版本、长度、序号和设备身份。慢连接时仅保留最新的一帧或最新的一个完整扫描，禁止可靠队列回放过期扫描。

### 4.2 传输选择

| 阶段 | 传输 | 连接发起方 | 认证与安全 | 用途 |
| --- | --- | --- | --- | --- |
| P3/P4 近场 | LAN TCP，采用长度定界 | 推荐 S3 主动连接 Windows bridge | 局域网令牌；TLS 是否启用由现场网络决定 | 最小可调试闭环 |
| P6 远程 | MQTT over TLS 或 WSS | 双端均主动连接公网 broker/relay | 每台车独立凭据、ACL 和证书校验 | 跨 Wi-Fi/NAT 的遥测与远程观察 |
| 禁止 | S3 直接发布/订阅跨网络 ROS2 DDS | 不适用 | 不适用 | DDS 的 UDP/组播发现不适合作为跨 NAT 网关协议 |

远程通道不可承担紧急停车或反射式避障。任何未来下行控制须另行设计租约、速率限制、超时、S3 仲裁和 STM32执行状态闭环。

## 5. 分阶段构建与审计

### P0：基线冻结与接口设计审计

**目标。** 确认活动源码、硬件接线、网络方式和数据合同，不写功能代码。

| 审计对象 | 要求 | 证据 |
| --- | --- | --- |
| 工作树 | 记录 `git status`、已修改文件和基线 commit；不覆盖用户已有改动 | 命令输出与变更清单 |
| 雷达型号 | 以实物标签确认 X3 或 X3 Pro、固件/序列号可得性、强度模式 | 设备照片/标签和抓包元数据 |
| UART/PWM | 复核 GPIO44 RX、共地、5 V 供电、GPIO4 PWM 保持现状 | 接线表、逻辑分析仪/万用表记录 |
| 帧资料 | 保存连续原始抓包，确认 `AA 55`、LSN、CS、2/3 字节样本模式和零位包 | 原始二进制文件、脚本输出、人工复核 |
| 网络 | 明确 LAN 测试或远程中继之一；登记 SSID/网段或 broker 域名/端口/凭据存储策略 | 网络拓扑与安全审计表 |
| 协议 | 审查并批准网关包字段、最大长度、丢弃策略、错误码、版本演进规则 | 独立协议评审记录 |
| STM32 边界 | 审查当前 SRPv4 不承载雷达原始数据；任何 `/cmd_vel` 下行延后 | 审查签字或 issue 记录 |

**P0 退出条件。** 已知准确的雷达包格式与网络路径；没有未解决的电平/供电/独占冲突；网关协议草案获得审核。未通过 P0，不进入解析或网络实现。

### P1：S3 雷达帧与健康度实现

**允许修改位置。** `ESPS3/main/radar/`、`ESPS3/main/CMakeLists.txt`，以及为受控测试新增的 S3 测试目录和文档。不得修改 GPIO4 PWM 常量、STM UART2 协议或 BLE 命令含义。

| 工作项 | 实施要求 | 审计检查 |
| --- | --- | --- |
| 编译归属 | 将 `radar_parser.c` 纳入实际 S3 组件构建；消除“源码存在但未链接”的假象 | 编译命令中出现该对象；ELF/map/编译日志可追溯 |
| 定界与校验 | UART 任意分块输入都应还原候选帧；仅在确认模式后启用 CS；统计 `valid/cs_error/header_resync/overflow` | 正常、拆分、拼接、噪声、错误 CS、最大长度、异常 LSN 测试 |
| 数据通道 | 解析器回调只写入有界 latest-only 包槽或小型队列；不得在 UART task 内执行 Wi-Fi 或 BLE 长操作 | 任务优先级、队列长度、锁等待和背压代码审计 |
| 诊断 | 以限流方式输出计数、帧率、最近有效帧年龄、UART 溢出、任务栈余量、内部/PSRAM 堆 | 长时间日志与 heap/stack 水位记录 |

**构建命令。** 在 `ESPS3/` 下加载固定 ESP-IDF 5.5.4 环境后运行 `idf.py build`。实施期间不新建任务命名的构建目录；审计记录使用活动 `build/` 的 `smartcar_s3_gateway.elf/.bin`、map 和构建日志。

**P1 退出条件。** host/组件测试覆盖异常字节流，S3 全量构建通过；台架抓包显示有效帧连续、checksum 错误和 UART 溢出可观测。此阶段仍不声明点角度、距离或网络传输已成功。

### P2：S3 Wi-Fi 上行实现

**允许修改位置。** 新增受控的 Wi-Fi/雷达上行组件；`ESPS3/main/CMakeLists.txt` 和 `main/idf_component.yml` 仅为新组件依赖服务。不得侵入 `stm_uart`、`smartcar_service` 的控制队列，且不得删除现有 BLE 日志能力。

| 工作项 | 实施要求 | 审计检查 |
| --- | --- | --- |
| 网络生命周期 | 明确 STA 获取 IP、断线、指数退避上限、DNS 失败、认证失败和重新连接状态 | 状态机测试与断网日志 |
| 上行工作者 | 独立低优先级 task 消费 latest-only 数据；连接慢或断线时不阻塞 UART task | 队列水位、丢弃数、最大等待和任务栈记录 |
| 报文编解码 | 先校验内部 YDLIDAR CS，再封装网关头；禁止把 `uart_read_bytes()` 的 512 B 块直接发出 | golden packet、长度/版本/CRC 拒绝测试 |
| 安全 | 凭据不写入日志或仓库；远程方案使用 TLS、设备唯一身份和最小 topic/endpoint 权限 | 配置泄露扫描、证书验证和 ACL 记录 |
| 共存 | BLE、Wi-Fi、雷达 UART 和 STM UART2 并发时，控制链路优先级不降低 | FreeRTOS 运行数据、STM 链路错误计数和 BLE 回归 |

**P2 退出条件。** S3 在网络断开与恢复期间持续接收雷达且不重启；雷达或网络慢速不会增加 STM UART2 错误、控制延迟或堆内存泄漏。仅有构建通过不能满足退出条件。

### P3：Windows ROS2 构建基线

**目标目录。** 后续获批后在 `ROS2_WIN/` 建立可复现工作区，建议目录：

```text
ROS2_WIN/
  docker/Dockerfile
  compose.yaml
  src/s3_ydlidar_bridge/
    package.xml
    CMakeLists.txt
    src/
    include/
    config/
    test/
```

| 工作项 | 实施要求 | 审计检查 |
| --- | --- | --- |
| 基础镜像 | 固定 Ubuntu 22.04 与 ROS2 Humble 的镜像摘要/版本；bridge、TF、SLAM 初期同一 ROS 域 | Dockerfile、镜像 digest、容器启动记录 |
| 依赖 | 使用 ROS2 标准消息、`rclcpp`、测试依赖；不复制或修改 vendor `ydlidar_ros2_driver` | `package.xml`、许可证清单、`rosdep` 与 `colcon` 日志 |
| 协议模块 | 单独实现网关帧 reassembly/验证，不把 TCP `recv()` 调用与 ROS publisher 耦合 | 拆包/粘包、错误长度、乱序、重复、断线重连单元测试 |
| 雷达解码 | 以官方 SDK/协议为对照，独立产生距离、角度和一圈扫描；转换使用米、弧度与明确 `frame_id` | 捕获回放与官方 SDK 输出对比；不以“画面看起来正确”作为验收 |
| `/scan` | 采用 SensorDataQoS 或明确等价 QoS；空点/无效量程行为显式定义 | `ros2 topic echo`、录包、字段断言 |

**构建命令。** 在容器 Linux 工作区内执行 `colcon build --symlink-install --packages-select s3_ydlidar_bridge`，随后执行 `colcon test --packages-select s3_ydlidar_bridge` 和 `colcon test-result --verbose`。这些命令必须记录容器镜像标识、ROS 发行版和依赖锁定信息。

**P3 退出条件。** bridge 可以离线回放 P0 捕获的二进制包并稳定发布语义正确的 `/scan`；此时不要求连车、不要求 STM32、也不允许发布运动控制。

### P4：近场端到端雷达链路

| 步骤 | 验收内容 | 证据 |
| --- | --- | --- |
| P4.1 | S3 与 Windows 同一 LAN，取得可追溯 IP/端口；bridge 建立连接 | 网络拓扑、连接日志 |
| P4.2 | S3 有效帧序号与 Windows 收到序号连续性可统计 | 两端计数和丢帧率 |
| P4.3 | 从 S3 收包到 ROS 发布的延迟、抖动和扫描年龄可观测 | 单调时间戳对照与 rosbag |
| P4.4 | `/scan` 的角度方向、量程、扫描频率、`frame_id` 与物理障碍物一致 | 定距目标实测、RViz 截图、原始抓包 |
| P4.5 | Wi-Fi 断开/重连、S3 重启、雷达断电后系统进入可见降级并恢复 | 故障注入日志和状态转换 |

P4 的通过标准是“可复现的传感器数据链路”，不是 SLAM、避障或车辆自动运动验收。

### P5：STM32 安全边界审计与构建

**本阶段默认不改 STM32 业务代码。** 目标是确保新增 S3 雷达/Wi-Fi 工作没有改变既有 STM32 安全属性，并为后续 `/cmd_vel` 网关建立冻结门槛。

| 审计项 | 当前约束 | P5 验证 |
| --- | --- | --- |
| 数据隔离 | 雷达原始包和 `/scan` 不进入 SRPv4/UART2 | 静态调用图、S3 发送点审查、UART2 带宽统计 |
| 链路不变量 | PA2/PA3 <-> GPIO17/18、921600 8N1、SRPv4 原有定义保持不变 | 配置/头文件差异审查与逻辑分析仪记录 |
| 最终停止权 | STM32 的 `motor_board_force_stop()`、姿态准入、链路超时、BUS_OFF 路径不得被 ROS2/S3 数据流绕过 | 源码审计、台架故障注入和电机零输出记录 |
| 控制扩展门槛 | 未来 ROS2 只能表达车体级速度意图；需频率、单位、上限、lease、超时、人工接管、E-stop 和执行反馈的独立协议审查 | 另立设计评审；P5 不批准自动运动 |

**构建命令。** 仅使用 CM7 既有规范：在 `STM32H757/CM7/` 下执行 `cmake --preset Debug`，随后执行 `cmake --build build/Debug --target Smart_Car_H757_CM7 -j2`。审计产物只认 `STM32H757/CM7/build/Debug/Smart_Car_H757_CM7.elf`；不得创建任务命名 build 目录。CM4 不是本雷达上行链路的必需构建目标。

**P5 退出条件。** CM7 Debug 构建通过，现有 S3-STM 协议与安全调用链无未批准变化；S3 Wi-Fi/雷达压力下 UART2 错误、链路状态和安全停止状态均有台架证据。该结果不授权车辆自动行驶。

### P6：SLAM、TF 与只读导航准备

只有 P4 与 P5 均通过后才进入本阶段。

| 依赖 | 要求 | 验收 |
| --- | --- | --- |
| 静态 TF | 测量并固定 `base_link -> laser_frame` 的安装平移与方向 | TF 树和实物量具记录 |
| 里程计 | 提供连续 `odom -> base_link`，注明轮速/IMU 来源、协方差和时间基准 | topic/TF 频率、时间戳与静态行驶对比 |
| SLAM Toolbox | 先手持或静止环境验证 `/scan` 与 TF，再做低速建图 | rosbag、地图一致性和失败日志 |
| Nav2 | 初期只运行 costmap/规划观察，不接通 S3-STM 控制 | 无运动模式配置、障碍物层截图和日志 |

## 6. 审计证据清单

每个阶段必须产生单独的证据条目，包含日期、操作者、Git commit、未提交差异、硬件版本、固件/镜像哈希、配置文件、命令、原始输出与结论。推荐按下表保存：

| 证据类别 | 最少内容 | 不能据此声称 |
| --- | --- | --- |
| 静态审计 | 文件路径、版本/长度/状态机/调用图检查 | 编译或设备行为 |
| S3 构建 | ESP-IDF 版本、命令、`elf/bin/map`、大小与警告 | flash、Wi-Fi、UART 或雷达通过 |
| ROS2 构建 | 镜像 digest、`colcon build/test`、依赖版本 | Windows 网络、真实 `/scan` 或 SLAM 成功 |
| CM7 构建 | Debug 配置、ELF、map、构建输出 | 串口、DMA、MotorBoard 或安全停止通过 |
| 台架链路 | 逻辑分析仪、两端计数、网络时间、原始包与 rosbag | 车辆可安全自动行驶 |
| 受控车辆 | 物理急停、速度上限、场地、观察者、版本、故障注入 | 对未测试场景的普遍安全保证 |

任何失败记录必须包含：失败阶段、复现步骤、原始日志/包、版本、错误计数、是否车辆上电或运动、临时缓解措施，以及恢复验证结果。

## 7. 风险与否决条件

| 风险 | 触发条件 | 处理/否决条件 |
| --- | --- | --- |
| 协议误判 | X3/X3 Pro 或强度模式未确认即解析 | 阻断 P1 解码和 P3 `/scan`，只允许保存原始包 |
| S3 资源竞争 | Wi-Fi/BLE 启用后 UART 溢出、控制任务栈下降或看门狗复位 | 阻断 P2/P4；先做任务、队列和内存隔离修复 |
| 旧扫描积压 | 网络断开后恢复时延迟持续增长 | 阻断 SLAM/避障；执行 latest-only 丢弃策略 |
| 跨网 DDS | 依赖 multicast/DDS 连接 S3 和 Windows | 不允许作为上行方案，改用 TCP/TLS 或 broker |
| STM32 边界被穿透 | 雷达流进入 UART2，或 ROS2 能直接控制执行器 | 阻断所有车辆测试，回退到安全审计 |
| 时间语义错误 | S3 时间与 ROS 时间混用且未测偏差 | 阻断 SLAM/里程计融合，仅允许诊断展示 |
| 未同步文档 | 实际源与 GPIO/PWM/构建说明不同 | 阻断发布；先同步文档并复审 |

## 8. 审批顺序与交付物

1. 批准 P0 的网络方式、网关协议草案、雷达模式和“雷达不上 STM32”边界。
2. 实施并独立审计 P1，形成 S3 帧完整性报告。
3. 实施并独立审计 P2/P3，分别形成 S3 网络报告和 ROS2 bridge 回放报告。
4. 在同一 LAN 执行 P4，形成端到端雷达数据报告。
5. 先执行 P5 安全边界审计，再准许 TF/SLAM 的 P6；Nav2 到车辆控制必须另开设计、实施和车辆验收任务。

本计划的首个可交付目标是：**Windows ROS2 稳定收到并记录语义正确的 `/scan`，同时 S3-STM32 原有安全控制链保持不变。**
