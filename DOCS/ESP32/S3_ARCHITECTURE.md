# ESP32-S3 软件架构规划

## 1. 文档范围与目录映射

本文件定义 Smart_Car 中 ESP32-S3（下称 S3）的**规划架构**，覆盖 L1
手机遥控和面向 L3 ROS2、SLAM、自动导航的扩展边界。它不创建 ESP-IDF
工程、不配置引脚、不实现通信或雷达解析，也不修改 `STM32H757/` 与
`ROS2_WIN/`。

用户目标文件为 `ESPS3/docs/S3_ARCHITECTURE.md`。当前 `ESPS3/` 只有空目录，
没有已确立的 ESP-IDF 文档结构；项目的既有文档权威位置是 `DOCS/`。因此本规划
暂存于 `DOCS/ESP32/S3_ARCHITECTURE.md`。未来创建并确认 S3 工程后，应以移动并
保留历史链接的方式映射到 `ESPS3/docs/S3_ARCHITECTURE.md`，而不是复制出两份
可漂移的架构事实。

## 2. 系统位置与责任边界

```text
iPhone App
  | BLE（近场控制）或 Wi-Fi（局域网控制）
  v
ESP32-S3 Gateway
  | 受统一控制协议约束的 UART
  v
STM32H757
  | 电机 / 编码器 / IMU 的低层实时控制

未来：YDLIDAR -> S3 -> Wi-Fi bridge -> ROS2_WIN -> SLAM / Nav2
```

S3 是手机通信中心、控制网关、STM32 通信桥，以及未来的雷达接入和 ROS2
桥接点。它负责接入会话、命令仲裁、协议帧校验、状态汇聚和上行转发；它不拥有
电机 PWM、编码器闭环、IMU 融合、路径规划、SLAM 或导航决策。

控制命令必须在 S3 经过来源、会话、模式、完整性、时效和安全状态检查后，才可
转交 STM32。STM32 仍是最后的低层执行和失联安全主体，不能将 S3 的在线状态视为
执行器安全证明。

## 3. 阶段目标

| 阶段 | S3 目标 | 允许控制来源 | 不在本阶段实现的内容 |
| --- | --- | --- | --- |
| L1 | BLE/Wi-Fi 接入、手动遥控仲裁、UART 桥接、基础状态反馈 | iPhone 的方向键或虚拟摇杆 | 自动驾驶、雷达解析、ROS2 节点、SLAM、导航 |
| L2（预留） | 雷达数据接入、状态/诊断扩展、ROS2 bridge 准备 | 手机仍为主控；受控诊断源可旁路只读 | 路径规划与无监督运动 |
| L3 | ROS2 bridge、传感器状态发布、自动控制来源仲裁 | 经授权且健康的 ROS2 自动控制或手机手动控制 | 将 Nav2 输出直接映射为电机电气动作 |

L3 的自动控制必须是新增的、显式受授权的控制来源；其优先级不得隐式覆盖急停或
本地人工接管。手机手动控制、自动控制和任何诊断控制均通过同一仲裁接口进入。

## 4. 规划中的 ESP-IDF 工程结构

以下为未来 `ESPS3/` 获得工程创建授权后的目标布局，不是本次创建的文件或目录：

```text
ESPS3/
  CMakeLists.txt
  sdkconfig.defaults
  main/
    app_main.c
    app_lifecycle.c
    component_dependencies.yml
  components/
    gateway_core/       # 生命周期、状态机、事件总线、命令仲裁
    control_protocol/   # 帧编解码、CRC、版本协商、命令/状态模型
    ble_transport/      # BLE GATT 会话、MTU/分片、认证接入
    wifi_transport/     # SoftAP/STA、IP 会话、受控网络传输
    stm32_link/         # UART DMA/RX、ACK、超时、重连与背压
    sensor_bridge/      # 预留的雷达/LiDAR 接口和上行数据抽象
    ros_bridge/         # 预留的 ROS2/网关外部协议适配层
    diagnostics/        # 指标、日志、健康度与故障快照
  docs/
    S3_ARCHITECTURE.md  # 本文未来迁移目标
  test/
```

组件之间通过小型、定长或上限明确的消息对象和队列通信。传输组件不得直接修改
执行状态，也不得绕过 `gateway_core` 向 `stm32_link` 发送控制帧。`control_protocol`
应成为 APP、S3、STM32、ROS2 bridge 的唯一帧模型入口，具体帧字段以
`SMART_CAR_PROTOCOL.md` 的后续批准版本为准。

## 5. FreeRTOS 任务与双核规划

ESP32-S3 采用双核，但 ESP-IDF Wi-Fi/BLE 系统任务的实际绑核、优先级和栈使用必须
以目标 ESP-IDF 版本、配置和运行时测量为准。下表是应用任务的逻辑分工，不宣称
系统任务已经按该表配置。

| 逻辑任务 | 建议核心 | 相对优先级 | 主要职责 | 输入/输出与约束 |
| --- | --- | --- | --- | --- |
| `control_supervisor` | Core 1 | 最高应用优先级 | 命令仲裁、会话租约、急停、看门超时 | 消费规范化控制命令；只产生批准/拒绝及安全动作 |
| `stm32_uart_rx` | Core 1 | 高 | UART 接收、帧边界、CRC 前置检查、状态入队 | ISR 仅搬运最小数据；不得在 ISR 中执行协议或业务逻辑 |
| `stm32_link_worker` | Core 1 | 高 | 控制帧发送、ACK、重试上限、链路状态 | 只接受 supervisor 已批准的控制意图 |
| `sensor_ingress` | Core 1 | 中 | 预留雷达/LiDAR 数据接收与有界缓冲 | 传感器数据可丢弃或降采样；永不挤占控制队列 |
| `ble_session_worker` | Core 0 | 中 | BLE 会话、分片重组、接入鉴权、上行状态 | 不直接执行控制；向 supervisor 提交规范化命令 |
| `wifi_session_worker` | Core 0 | 中 | Wi-Fi 连接、网络会话、可靠状态/诊断上行 | 控制通道要有独立限流和背压，不被大数据流阻塞 |
| `telemetry_worker` | Core 0 | 低 | 状态聚合、诊断、日志与指标输出 | 可合并、降采样或丢弃低优先级遥测 |
| `lifecycle_worker` | Core 0 | 中 | 启动顺序、配置、错误恢复和服务启停 | 状态转换必须通知 supervisor |

应用核心分工以“Core 1 保持控制路径确定性、Core 0 承载无线与低优先级工作”为
目标。任何实际任务栈、核心占用、Wi-Fi/BLE 共存行为和中断延迟都需要构建后实测；
禁止仅因架构表存在就假定实时性。

## 6. 通信模块设计

### 6.1 BLE

BLE 面向近场配网、L1 低带宽遥控和基础状态订阅。设计应分离：

- 接入与授权：设备身份、配对/会话建立、控制权租约；
- 控制：小型、带序号和时效的控制命令；
- 状态：订阅式、可降采样的状态反馈；
- 诊断：与控制特征分离，限流且不可影响急停和控制心跳。

BLE 断开、会话失效、序号倒退、分片不完整或命令过期时，必须撤销该来源的控制权。
BLE 不负责替 STM32 维持运动；状态丢失和重连均不得恢复旧速度命令。

### 6.2 Wi-Fi

Wi-Fi 用于 L1 局域网控制/状态、较大诊断数据，以及 L3 ROS2 bridge 的承载网络。
网络角色（SoftAP、STA 或受控双角色）、安全策略、IP 发现和具体上层传输协议仍待
单独设计。无论选型如何，网络控制消息须经过与 BLE 相同的身份、会话、时效和仲裁
链路；传感器流、日志或雷达数据不得与控制消息共享无界队列。

L3 的 ROS2 不是让 S3 直接承担 SLAM/导航计算的理由。`ros_bridge` 仅负责版本化
网关协议、状态和传感器数据适配，以及把经过安全仲裁的高层运动意图提交给
`control_supervisor`。

### 6.3 S3 到 STM32 的 UART 边界

UART 是 S3 与 STM32 的计划控制桥。它应具备独立收发缓冲、帧定界、长度上限、版本、
序列号、CRC、ACK/NACK、心跳、重发次数上限和链路状态机。S3 发送的是已仲裁的
`control intent`，而不是 PWM、方向电平或电机驱动细节；STM32 反馈执行状态、故障、
急停/超时状态和必要的传感器摘要。

当前 STM32 文档已经记录 `PD3/PD4` 不能构成 UART TX/RX 对。该物理路由问题是 L1
串口落地的阻断项：在硬件有效引脚、3.3 V 电平、共地、波特率、流控和复位策略完成
确认前，本规划不主张启用 UART 或宣称端到端控制可用。

### 6.4 雷达/LiDAR 与 ROS2 预留

`sensor_bridge` 为 YDLIDAR X3/X3 Pro 等传感器保留独立接口、时间戳、数据来源、
健康度、背压和失效状态。一个物理串口在任一时刻只由一个消费者管理；雷达原始帧
解析、扫描模型和 ROS `LaserScan` 转换均不在 L1 实现范围。

未来 S3 网关路线为：`LiDAR -> sensor_bridge -> Wi-Fi bridge -> ROS2_WIN`。需在
后续协议任务决定传输的是原始帧、标准化扫描点还是摘要，并分别验证带宽、时间同步、
丢包策略和 ROS2 兼容性。不得让 Windows/Docker 与 S3 并发占用同一雷达 UART。

## 7. 控制与传输安全边界

1. **急停优先。** 本地急停、来自手机的急停和 STM32 故障状态优先于一切手动或自动
   控制；急停可抢占普通队列并要求明确确认后才允许恢复。
2. **来源仲裁。** 任一时刻只允许一个获授权的运动控制来源；状态订阅可多客户端并发。
3. **时效失效。** 控制消息、心跳和 ACK 均带单调序号与截止时间。超过租约或心跳窗口
   即发送/维持安全停止请求，不缓存旧速度等待恢复。
4. **链路降级。** BLE/Wi-Fi 断开只撤销相应来源；S3 到 STM32 链路异常、执行状态过期
   或 STM32 报告故障时，S3 进入 `FAULT_SAFE`，拒绝新的运动命令。
5. **资源隔离。** 控制、状态、传感器和诊断使用有界且分离的缓冲；低优先级数据优先
   降采样或丢弃，绝不通过无限重试、无限队列或提高栈大小掩盖拥塞。
6. **故障可见。** 协议错误、CRC 失败、队列水位、重试耗尽、控制来源切换和安全停止
   原因应形成结构化诊断事件；诊断记录不得包含密钥或完整凭据。

具体命令号、帧长度、CRC 算法、心跳周期和状态字段由后续
`SMART_CAR_PROTOCOL.md` 统一定义，本文件不另行生成冲突的协议真值。

## 8. 生命周期、错误状态与依赖

```text
BOOT -> SELF_CHECK -> PROVISIONING / CONNECTING -> READY
                                             |          |
                                             v          v
                                         DEGRADED <- FAULT_SAFE
                                             |          |
                                             +---- recovery ----+
```

| 状态 | 条件 | 允许行为 | 退出条件 |
| --- | --- | --- | --- |
| `BOOT` | 复位后 | 最小硬件和持久配置初始化 | 基础自检完成 |
| `SELF_CHECK` | 检查存储、任务、传输依赖 | 只报告诊断，不接受运动控制 | 关键依赖通过或进入安全故障 |
| `PROVISIONING` / `CONNECTING` | 等待 BLE/Wi-Fi 接入或 STM32 链路建立 | 可配网、只读诊断 | 建立有效控制会话和安全链路 |
| `READY` | 安全链路健康且有能力接受控制 | 可仲裁和转发当前控制来源 | 任一关键健康条件失效 |
| `DEGRADED` | 非关键上行、传感器或单一传输异常 | 保留已确认安全能力，禁止受影响能力 | 明确恢复或升级为 `FAULT_SAFE` |
| `FAULT_SAFE` | 急停、UART 失联、STM32 故障、控制超时或完整性失败 | 拒绝运动意图，维持/请求安全停止，保留诊断 | 故障已确认消除且经显式恢复流程 |

主要依赖包括 ESP-IDF/FreeRTOS、ESP32-S3 支持的 BLE 与 Wi-Fi 组件、被批准的统一协议、
已确认的 STM32 物理 UART 路由，以及未来雷达接口和 ROS2 bridge 契约。第三方库、
分区方案、NVS/证书策略、BLE 安全等级、网络服务端口及 ROS2 数据编码均尚未选择，
不可在未授权实现阶段自行引入。

## 9. 后续实施门槛与验证边界

建议按以下顺序开展独立授权的实施任务：

1. 先解决并记录 STM32-S3 的有效物理串口路由和电气条件；冻结统一协议与安全时序。
2. 建立最小 ESP-IDF 工程、生命周期和无执行器的 UART 协议模拟测试。
3. 单独接入 BLE、Wi-Fi 与控制仲裁，并以模拟 STM32 验证断联、超时和急停。
4. 在静止、可物理断电的受控环境做端到端车体安全测试后，再接入雷达与 ROS2。
5. 在 L1 的手动接管、停止、状态时效和日志可追溯性稳定后，才授权 L3 的 ROS2/SLAM/
   自动导航控制来源。

本文件的证据等级为**静态架构规划**：确认了本仓库既有责任边界、文档位置和 STM32
串口路由阻断记录。它不证明 ESP-IDF 可构建、双核任务实际运行、RAM/PSRAM 足够、
BLE/Wi-Fi 延迟、UART 收发、雷达可用、ROS2 互通、急停时延或车辆运动安全。上述均须
由后续构建、台架、硬件与集成测试分别获得证据。
