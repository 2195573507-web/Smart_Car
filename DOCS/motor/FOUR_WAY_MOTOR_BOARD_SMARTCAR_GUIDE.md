# Smart_Car 四路电机驱动板详细接入指南

状态：`CONFIRMED（资料审阅）` + `PLANNED（项目接入方案）`

版本基线：四路电机驱动板资料目录中标注的“2026.6.24 及之后下单客户”资料；
Smart_Car 当前工作区状态以 2026-08-20 现场检查结果为准。

本指南的目标是让后续开发人员能够从板卡识别、供电和接线开始，完成参数配置、
串口/I2C 控制、编码器读取、STM32H757 分层接入和逐级验证。指南不声称已经完成
代码接入、烧录、串口抓包、编码器读数或车辆运行验收。

## 1. 先看结论

### 1.1 板卡能做什么

官方资料把板卡定义为四路有刷直流电机驱动模块，板上协处理器负责：

- 四路电机输出，通道标号为 `M1`、`M2`、`M3`、`M4`。
- 带编码器电机的速度闭环控制。
- 编码器总脉冲、10 ms 实时脉冲和速度数据读取。
- 通过 USB Type-C 对板卡固件进行更新。
- 通过 TTL 串口或 I2C 与外部主控通信。

### 1.2 对 Smart_Car 的直接影响

| 项目 | 当前事实 | 对接结论 |
| --- | --- | --- |
| STM32 最终运动权威 | Smart_Car 已确定由 STM32H757 负责安全和最终运动决策 | 电机板只能作为执行器/编码器外设，不能成为安全策略拥有者 |
| STM32 USART2 | 当前用于 STM32 <-> ESP32-S3，`PA2/PA3`，源代码配置 921600 | **不能直接拿来接电机板** |
| STM32 I2C4 | 当前用于 LSM303，`PD12/PD13` | 不能在没有总线互斥、地址和电气确认前直接并接 |
| STM32 TIM3 PWM | `PC6..PC9` 为四路本地 PWM 预留 | 若使用串口候选 `USART6` 的 `PC6/PC7`，必须先做 IOC/所有权决策 |
| ESP32-S3 UART2 | 当前为 STM 链路 `GPIO17/18` | 不应把电机板接入该口而破坏 STM-S3 链路 |
| ESP32-S3 UART1 | 当前为雷达链路，RX `GPIO44` | 与电机板无关，必须保持隔离 |
| 当前电机驱动代码 | `STM32H757/Drivers/Motor` 仍是占位 API | 没有现成可调用的电机板驱动 |
| 已有设计文档 | `DOCS/superpowers/specs/2026-08-09-stm32h757-motor-board-uart-design.md` 提出 `USART6 PC6/PC7` 候选 | 这是实现规划，不是当前运行事实；该设计当时还没有厂商协议证据 |

### 1.3 推荐的第一阶段方案

建议先选 **TTL 串口直连 STM32H757**，并使用独立的 USART 外设。理由是：

1. 官方串口命令可读、可抓包、可用 PC 上位机快速验证。
2. 串口协议覆盖配置、控制、反馈、Flash 查询和电池查询；I2C 表没有给出 PID、Flash 查询和恢复出厂寄存器。
3. 不需要把电机板 I2C 接到已经承载 LSM303 的 I2C4。
4. 可先用 `$pwm:0,0,0,0#` 做安全停止和原始协议验证，再启用速度闭环。

候选硬件路线为已有设计文档提出的 `USART6`：

| 电机板信号 | STM32H757 候选 | 方向 | 说明 |
| --- | --- | --- | --- |
| `TX2` | `PC7 / USART6_RX` | 板 -> STM32 | 接收反馈 |
| `RX2` | `PC6 / USART6_TX` | STM32 -> 板 | 发送命令 |
| `GND` | 系统地 | 共地 | 必须确认电平和地线质量 |
| `5V` | 板卡逻辑供电输入/输出按实物确认 | 电源 | 不要把 5 V 输出能力当作电机电源 |

上表是 `PLANNED`，因为当前 IOC 仍把 `PC6/PC7` 配置为 `TIM3_CH1/CH2`，且尚未看到
USART6 初始化和运行调用。实施前必须先确认 PCB 引脚、连接器丝印、电平和 IOC 所有权。

## 3. 板卡硬件和电气事实

### 3.1 官方规格

| 项目 | 官方资料给出的值 | 使用时的工程含义 |
| --- | --- | --- |
| 推荐电源输入 | `5-12 V` | 这是板卡输入范围描述，不等于所有电机都能用同一电压 |
| 5 V 引脚输出 | `0.7 A` | 只可作为逻辑/外设供电参考，需确认具体版本和温升 |
| 3.3 V 引脚输出 | `500 mA` | 不应直接按最大值长期取电；先核对主控板电流需求 |
| 单路持续驱动电流 | 默认 `4 A`，最大可输出 `5.5 A` | 电机堵转电流和峰值必须小于板卡、电源、线束和连接器能力 |
| 外形 | `56 x 65 x 13.4 mm` | STEP 模型可用于机械布局，不能替代实物孔位核对 |
| 编码器接口 | `PH2.0-6PIN`、杜邦插座 | 编码器电源、A/B 相、地必须按电机和线束逐根核对 |
| 无编码器电机接口 | `XH2.54-2PIN` | 仅连接电机动力线，不要把编码器电机插入此接口 |
| 串口物理接口 | 右侧 `PH2.0` 串口口、USB Type-C 串口口 | 两者都属于串口接入路径；是否同时接入、Type-C 转换芯片和复位行为需按实物/抓包确认 |
| I2C 物理接口 | 右侧 `PH2.0` I2C 口 | 与串口二选一；SDA/SCL 电平、上拉和线序必须实测 |
| 电源输入接口 | 底部 `5-12 V` 螺丝端子 | 正负极和电源能力必须按丝印与实物复核 |
| 通信方式 | TTL 串口或 I2C，二选一 | 官方资料明确说 I2C 与串口不能共用 |
| 电机通道数 | 4 | `M1..M4` 的逻辑编号固定，不能按车体坐标自行重排而不留映射 |

### 3.2 M1-M4 车体映射

官方资料定义：

| 板卡通道 | 小车位置 | Smart_Car 建议逻辑名 |
| --- | --- | --- |
| `M1` | 左上，左前轮 | `LF` |
| `M2` | 左下，左后轮 | `LR` |
| `M3` | 右上，右前轮 | `RF` |
| `M4` | 右下，右后轮 | `RR` |

建议在项目中同时保留 `motor_index=M1..M4` 和 `wheel=LF/LR/RF/RR` 两个字段，禁止
只用数组下标传递而没有名称。所有速度、PWM、编码器和故障数据都应带通道编号。

### 3.3 电机供电和参数

官方《常用电机介绍以及用法》给出的主要参数如下。参数是资料值，最终仍需以你手上的
电机标签、订单型号和实测电流为准。

| 电机 | `mtype` 常用值 | 额定/推荐电压 | 减速比 `mphase` | 磁环线数 `mline` | 编码器 | 推荐控制 |
| --- | ---: | --- | ---: | ---: | --- | --- |
| 520 MD520Z19/30/56 | `1` 或按线序选择 `2` | 12 V；资料建议 11-16 V，推荐 12 V | 19/30/56 | 11 | AB 增量霍尔 | `$spd` |
| 310 MD310Z20 | `2` | 7.4 V；资料建议 4.2-8.4 V | 20 | 13 | AB 增量霍尔 | `$spd` |
| 直流 TT | `4` | 6 V 电机，资料建议 7.4 V | 48 | 不适用 | 无 | `$pwm` |
| 编码器测速 TT | `3` | 6 V 电机，资料建议 7.4 V | 45 | 13 | AB 霍尔 | `$spd` |
| L 型 520 | `1` 或按线序选择 `2` | 12 V | 40 | 11 | AB 霍尔 | `$spd` |

注意：官方资料的“520/310 类型”同时承担编码器 A/B 相位配置作用，因此 `mtype`
不能简单理解为电机铭牌型号。520 电机使用 PH2.0 黑色双头线时，资料说明电机 A
可能接到板卡 B、B 接到 A，此时选择 `$mtype:1#`；使用 A-A、B-B 的杜邦接线时，
资料建议选择 `$mtype:2#`。这不是通用规律，必须以实际 A/B 线序和正转方向实测确认。

### 3.4 电气安全要求

1. 电机额定电压、堵转电流、额定电流和板卡输入电压必须分别核对，不能只看“5-12 V”就直接接 12 V。
2. 供电电源要能承受四路同时启动和堵转瞬态；电源限流、降压和电池保护不能省略。
3. 逻辑串口必须共地，TX/RX 交叉连接；不能把 5 V TTL 信号直接接入只允许 3.3 V 的 STM32 引脚。
4. 板卡 `5V`/`3V3` 引脚的输出能力是辅助供电指标，不代表可以给四个电机供电。
5. 首次接线时电机轮子必须离地或机械脱开，先用 `$pwm:0,0,0,0#` 验证通信，再逐路小幅度驱动。
6. 板卡、主控、电机电源和 USB 调试线连接前，先确认共地和电源极性；不要在电机带载时插拔编码器线。

## 4. 串口协议完整说明

### 4.1 物理配置

官方串口配置：

```text
115200 baud, 8 data bits, no parity, no hardware flow control, 1 stop bit
```

命令为 ASCII 文本，以 `$` 开始、以 `#` 结束。官方资料说命令不区分大小写；建议
项目统一发送小写命令，接收端对命令名做大小写兼容。配置命令成功时通常返回“命令
+OK”或 `OK!` 一类确认；速度/PWM 命令官方说明没有返回内容，不能用“没有 ACK”
判断电机没有动作。

### 4.2 配置命令

| 命令 | 参数 | 默认/范围 | 是否掉电保存 | 含义 |
| --- | --- | --- | --- | --- |
| `$mtype:x#` | `1..4` | 见电机类型表 | 是 | 电机类型/编码器相位配置 |
| `$deadzone:xxxx#` | 整数 | 默认约 `1600`，`0..3600` | 是 | PWM 死区，需实测电机刚开始转动的阈值 |
| `$mline:xx#` | 整数 | 资料示例 `11/13` | 是 | 编码器磁环线数/相位线参数 |
| `$mphase:xx#` | 整数 | 资料默认约 `30` | 是 | 电机减速比 |
| `$wdiameter:xx#` | 浮点，mm | 例 `50`、`67` | 是 | 轮径，用于速度换算 |
| `$mpid:P,I,D#` | 三个浮点 | 默认资料示例 `P=0.8,I=0.06,D=0.5` | 是 | 带编码器电机的速度 PID |
| `$flash_reset#` | 无 | - | 触发重启 | 恢复所有变量出厂值 |

重要资料差异：

- PDF 的命令表和示例源码均把 `$mline` 用作磁环/相位线，把 `$mphase` 用作减速比。
- 正式 `串口通信协议.xlsx` 的 `$mline` 备注把它写成“减速比参数”，与 PDF 文字冲突；
  示例函数 `send_pulse_line()`/`send_pulse_phase()` 也容易让名称误导。
- 本项目应以物理参数含义和寄存器 `0x03/0x04` 为准：`mline=磁环线数`，`mphase=减速比`。
- 修改 PID 时板卡会重启并停止正在运动的电机；配置任务必须先发停止命令并等待重启后再继续。

### 4.3 运动命令

| 命令 | 范围 | 适用 | 说明 |
| --- | --- | --- | --- |
| `$spd:m1,m2,m3,m4#` | 每路 `-1000..1000` | 带编码器电机 | 速度闭环；平台资料把单位解释为 mm/s，控制指令 PDF 只写“mm”，需实测确认 |
| `$pwm:m1,m2,m3,m4#` | 每路 `-3600..3600` | 有/无编码器均可 | 直接 PWM；无编码器电机必须使用此模式 |

符号代表方向，顺序始终为 `M1,M2,M3,M4`。负号的实际车轮方向取决于电机安装朝向和
编码器 A/B 线序，不能仅按“负数=车体后退”推断。

官方控制指令 PDF 的 PWM 示例行误写成 `$spd:0,-520,300,800#`；PC 上位机资料、
示例源码和命令名称均表明这里应为 `$pwm:0,-520,300,800#`，实现时必须使用 `$pwm`。

安全要点：

- `$spd:0,0,0,0#` 会让速度 PID 继续生效，官方说明此时手动拧轮可能感觉被锁住。
- 需要让电机输出归零并允许机械自由转动时，使用 `$pwm:0,0,0,0#`。
- 上层急停必须由 STM32 本地安全策略直接触发，不能依赖 BLE、ROS2 或 App 的网络往返。
- 运动命令无返回是协议行为；应由周期性编码器/速度反馈和链路健康状态判断结果。

### 4.4 反馈和查询命令

#### 上传开关

```text
$upload:all_encoder,ten_ms_encoder,speed#
```

三个字段均为 `0/1`：

1. 总编码器脉冲。
2. 10 ms 实时编码器增量。
3. 电机速度。

例如 `$upload:0,1,0#` 只打开 10 ms 实时增量反馈，`$upload:0,0,0#` 关闭反馈。
反馈格式为：

```text
$MAll:M1,M2,M3,M4#    // 累计编码器
$MTEP:M1,M2,M3,M4#    // 10 ms 相对脉冲
$MSPD:M1,M2,M3,M4#    // 速度
```

反馈解析器必须：

- 以 `$`/`#` 做边界，不依赖单次 UART read 的完整性。
- 丢弃字段数不是 4、含非法字符、溢出或超时的帧。
- 对总脉冲和 10 ms 脉冲使用有符号值；不能把负向转动当作无符号大数。
- 在数据结构中记录接收时间、通道编号、数据类型和解析错误原因。

#### 查询

| 命令 | 返回 | 说明 |
| --- | --- | --- |
| `$read_flash#` | Flash 变量文本 + OK 类确认 | 用于核对类型、死区、线数、减速比、轮径、PID 是否落盘 |
| `$read_vol#` | `$Battery:7.40V#` 形式 | 电池电量文本；单位和精度按返回字符串解析 |

### 4.5 推荐串口初始化/配置序列

下面是 `PLANNED` 的安全配置流程，不是当前项目已实现代码：

```text
1. 建立 UART 115200 8N1，清空 RX 缓冲。
2. 发送 $pwm:0,0,0,0#，等待 TX 完成。
3. 发送 $read_flash#，保存原始返回和时间戳。
4. 仅对确需修改的参数发送 mtype/deadzone/mline/mphase/wdiameter。
5. 每条配置等待 OK 类确认；超时则停止后重试，禁止连续盲发。
6. 如修改 MPID 或 flash_reset，等待板卡重启，再重新建立链路。
7. 发送 $read_flash#，逐字段核对写入值。
8. 发送 $upload:0,1,1#，确认 MTEP/MSPD 反馈格式。
9. 先单路发送低幅值 PWM，确认方向和停止，再切换到 $spd。
```

示例源码大量使用 `100 ms` 固定延时。项目实现应以“收到确认/超时状态机”为主，
固定延时只作为最小保护间隔，不能替代协议确认。

## 5. I2C 协议完整说明

### 5.1 总线参数

- 7 位从机地址：`0x26`。
- 线上的写地址通常为 `(0x26 << 1) | 0 = 0x4C`，读地址为 `0x4D`；使用 STM32 HAL 时传入的 `DevAddress` 要按 HAL 约定传 8 位左移值。
- 官方平台示例常用 `400 kHz`，但板卡 PDF 没有在协议表中强制给出速度；先从 `100 kHz` 验证，再按波形和上拉能力提高。
- I2C 与板卡串口不能同时使用，二选一。
- 写事务：`START -> SLA+W -> register -> payload -> STOP`。
- 读事务：`START -> SLA+W -> register -> repeated START -> SLA+R -> data -> NACK -> STOP`。

### 5.2 寄存器表

| 寄存器 | 方向 | 数据 | 范围/长度 | 语义 |
| --- | --- | --- | --- | --- |
| `0x01` | W | `uint8` | `1..4` | 电机类型 |
| `0x02` | W | `uint16` | `0..3600` | PWM 死区，大端 |
| `0x03` | W | `uint16` | `0..65535` | 磁环线数，大端 |
| `0x04` | W | `uint16` | `0..65535` | 减速比，大端 |
| `0x05` | W | `float32` | 4 字节 | 轮径 mm，小端 IEEE-754 |
| `0x06` | W | 4 x `int16` | `-1000..1000` | 四路速度，大端，每路 2 字节 |
| `0x07` | W | 4 x `int16` | `-3600..3600` | 四路 PWM，大端，每路 2 字节 |
| `0x08` | R | `uint16` | 2 字节 | 电池电压，`(buf[0]<<8\|buf[1])/10.0` |
| `0x10..0x13` | R | `int16` | 每路 2 字节 | M1-M4 的 10 ms 实时脉冲 |
| `0x20/0x21` | R | 2 x `uint16` | 4 字节合成 | M1 总脉冲高/低字 |
| `0x22/0x23` | R | 2 x `uint16` | 4 字节合成 | M2 总脉冲高/低字 |
| `0x24/0x25` | R | 2 x `uint16` | 4 字节合成 | M3 总脉冲高/低字 |
| `0x26/0x27` | R | 2 x `uint16` | 4 字节合成 | M4 总脉冲高/低字 |

总脉冲合成：

```c
uint16_t hi = ((uint16_t)buf_hi[0] << 8) | buf_hi[1];
uint16_t lo = ((uint16_t)buf_lo[0] << 8) | buf_lo[1];
int32_t total = (int32_t)(((uint32_t)hi << 16) | lo);
```

10 ms 脉冲解析：

```c
int16_t delta = (int16_t)(((uint16_t)buf[0] << 8) | buf[1]);
```

四路速度/PWM 示例，M1=200、M2=-200、M3=0、M4=500：

```text
00 C8 FF 38 00 00 01 F4
```

轮径写入必须显式按小端序列化，不能直接依赖结构体布局：

```c
uint8_t bytes[4];
memcpy(bytes, &wheel_diameter_mm, sizeof bytes); // 仅在目标已确认 IEEE-754 little-endian 时使用
```

更稳妥的实现是使用 `static_assert(sizeof(float) == 4)`，并明确写出小端转换函数。

### 5.3 I2C 表的缺口和注意事项

- 正式 I2C 表没有给出 PID、Flash 查询、恢复出厂的寄存器；这些能力应优先走串口，
  不要自行猜测未公开寄存器。
- 正式 I2C 表把 `0x20..0x27` 的高字/低字类型标为 `int16_t`，但同一页的计算式要求
  将四个原始字节按 `high << 24 | high_low << 16 | low_high << 8 | low_low` 拼成
  32 位总脉冲。因此实现应把每次寄存器读回当作两个原始字节，禁止先对高字做有符号
  扩展再拼接。
- 部分旧 C 示例把 `MOTOR_TYPE` 写成长度 2，但实际只发送 1 个字节；项目实现必须按正式表发送 1 字节并验证 ACK。
- 旧 C 示例中的 `char2float()` 使用动态内存转换，不能照搬到实时任务；H757 使用固定缓冲和显式字节序。
- 厂商示例直接连续读取高/低寄存器；在高速运动时可能跨越计数更新，项目需要定义一致性策略（例如先后两次读取高字并比较，或接受采样瞬间误差并记录时间戳）。

## 6. Smart_Car 接入架构

### 6.1 当前代码事实

当前 Smart_Car 的相关边界：

- `STM32H757/Drivers/Motor/motor.c/.h`：占位电机驱动接口。
- `STM32H757/BSP/PWM/bsp_pwm.c/.h`：持有 TIM3 CH1-CH4 本地 PWM BSP。
- `STM32H757/Middleware/Communication/UART_Link/uart_link.c/.h`：持有 USART2、921600、DMA、环形缓冲；用途是 STM-S3 链路。
- `STM32H757/CM7/Core/Src/main.c`：初始化 I2C4、TIM1、TIM3、TIM2、USART1，并启动 IMU/UART/S3 服务；当前没有 USART6 电机板初始化。
- `STM32H757/Smart_Car_H757.ioc`：PC6/PC7/PC8/PC9 是 TIM3 PWM，PD12/PD13 是 LSM303 的 I2C4，PA2/PA3 是 S3 UART2。
- `DOCS/superpowers/specs/2026-08-09-stm32h757-motor-board-uart-design.md`：提出独立 `Middleware/MotorBoard` 和 USART6 PC6/PC7 候选，但协议当时未定义。

### 6.2 推荐的模块边界

后续实现建议新增独立目录，不把厂商 ASCII 命令散落到 Chassis、S3 service 或 App：

```text
STM32H757/Middleware/MotorBoard/
  motor_board_transport_uart.c/.h   // USART6 或经批准的独立 UART，收发和超时
  motor_board_protocol.c/.h         // ASCII 帧编码、边界、字段和反馈解析
  motor_board_config.c/.h           // 参数配置、读取回读、配置版本
  motor_board.c/.h                  // 生命周期、状态、命令入口、故障降级
```

建议的调用方向：

```text
App/S3 控制意图
    -> STM32 本地安全限幅/模式检查
    -> Chassis/Motion
    -> MotorBoard API（速度或 PWM）
    -> MotorBoard Protocol
    -> MotorBoard UART
    -> 四路电机驱动板
    <- MTEP/MSPD/MAll/Battery
    <- Encoder/Odometry/Telemetry
```

Transport 层不得决定速度上限、急停条件或车体运动学；Protocol 层不得直接操作 HAL；
应用层不得拼接 `$spd` 字符串。

### 6.3 生命周期状态机

```text
POWER_OFF
  -> LINK_PROBE
  -> SAFE_STOP_SENT
  -> CONFIG_READ
  -> CONFIG_VERIFY
  -> READY
  -> COMMANDING
  -> FEEDBACK_VALID

任意状态 -- UART 超时/格式错误/电源异常 --> DEGRADED_STOP
DEGRADED_STOP -- 明确重连且重新验证 --> LINK_PROBE
```

状态转换建议：

| 状态 | 进入条件 | 允许动作 | 离开条件 |
| --- | --- | --- | --- |
| `LINK_PROBE` | UART 初始化完成 | 发送查询/停止，收集原始字节 | 收到合法确认或超时 |
| `SAFE_STOP_SENT` | 已发送 PWM 零 | 禁止非零运动 | 链路和停止命令完成 |
| `CONFIG_VERIFY` | 已读 Flash/参数 | 只允许配置帧 | 所有必需字段一致 |
| `READY` | 参数合法、反馈时间有效 | 接收受限运动请求 | 首个有效控制周期 |
| `COMMANDING` | 已发送速度/PWM | 周期性命令和反馈 | 超时/急停/故障 |
| `DEGRADED_STOP` | 链路/反馈/电源不可信 | 发送有限次停止，禁止重新加速 | 人工或系统明确重连 |

### 6.4 命令调度和资源约束

- 串口 115200 的有效吞吐约为 11.5 kB/s（按 8N1 粗略估计）；必须计算控制帧和反馈帧总带宽，不能无上限开启三种上传。
- 控制周期建议先从 20-50 ms（50-25 Hz）开始，待逻辑分析仪确认余量后再提高；这是 `PLANNED` 参数，不是厂商固定要求。
- 发送任务使用固定大小 TX 缓冲、互斥锁和有限超时；禁止在 ISR 中 `sprintf`、等待 TXE 或调用阻塞 I2C。
- 接收使用环形缓冲和按 `$...#` 的流式解析；不假设一次 DMA/Read 恰好得到一帧。
- H7 若使用 DMA，DMA 缓冲必须遵守 D-Cache 对齐/失效规则；当前 USART2 的 DMA 处理不能直接复制后改串口号而忽略所有权。
- I2C 方案必须给 I2C4 总线加互斥锁，并协调 LSM303 采样、超时和错误恢复；不要在 IMU 任务中同步等待多个电机寄存器读取。
- 编码器总脉冲为 32 位有符号值，应用层使用 `int32_t`；不要使用 `int` 依赖编译器宽度。
- 所有日志包含通道、状态、命令类型、超时和错误原因，日志长度受现有 Smart_Car 限制约束。

## 7. 推荐实施步骤

### 阶段 A：不改代码的硬件与资源确认

1. 记录板卡版本、订单日期、固件版本和 `YB-ESF01-V2.0.STEP` 对应机械版本。
2. 记录每个轮子的电机型号、额定电压、堵转电流、减速比、磁环线数、A/B 线序。
3. 记录四路 M1-M4 到 LF/LR/RF/RR 的实际安装映射。
4. 用万用表确认主控 IO 电平、板卡 TX/RX 空闲电平、共地和电源极性。
5. 选择串口或 I2C，不得同时连接两条板卡控制链路。
6. 对 USART6 PC6/PC7 方案检查 PCB 引脚和 `TIM3` 使用者；若保留本地 PWM，则另选独立 UART。
7. 对 I2C4 方案检查 LSM303 地址、上拉、电容、总线锁和采样时序；未经批准不得改动 PD12/PD13。

### 阶段 B：PC 独立验证

使用 `6.附件/串口助手/UartAssist 5.0.3.exe` 或等效串口工具：

1. 板卡只接逻辑电源和 USB/串口，电机轮子离地。
2. 设置 115200 8N1、无流控。
3. 发送 `$read_flash#`，保存原始响应。
4. 发送 `$pwm:0,0,0,0#`，确认无误动作。
5. 逐条配置一个已知电机参数，等待确认，再用 `$read_flash#` 回读。
6. 发送 `$upload:0,1,1#`，记录 MTEP/MSPD 的字段格式和周期。
7. 发送 `$read_vol#`，记录电压文本。
8. 用单路、低幅值 `$pwm` 验证正负方向；每次只改变一个 M 通道。

PC 验证结果必须保存为带时间戳的原始串口日志，不能只保存截图。

### 阶段 C：STM32H757 原始传输层

实施位置、原因、潜在影响和验证方式：

| 项目 | 内容 |
| --- | --- |
| 修改位置 | `STM32H757/Middleware/MotorBoard/`、经批准的 IOC/生成初始化文件、CM7 CMake 源列表 |
| 修改原因 | 为板卡提供独立 UART 资源、流式协议解析和有限超时 |
| 修改内容 | 新增 transport/protocol/config/driver 四层；不修改 App BLE、STM-S3 SCBP-V3 和雷达链路 |
| 潜在影响 | USART6/PC6/PC7 与 TIM3 冲突；UART 任务、DMA、日志和电机命令可能增加 RAM/CPU 占用；错误处理不当会阻塞 RTOS |
| 验证方法 | 静态检查、CM7 编译、桌面协议单元测试、逻辑分析仪 115200 波形和 RX/TX 抓包；硬件动作另行验收 |

第一版只实现：

- 原始发送 `$pwm:0,0,0,0#`、`$read_flash#`、`$read_vol#`。
- 帧边界、字段计数、整数溢出、字符串长度和超时处理。
- 反馈保存和解析，不直接进入运动闭环。

### 阶段 D：配置和反馈接入

1. 先把每个轮子的配置作为版本化结构保存到非易失存储，不要每次启动盲写 Flash。
2. 启动时读板卡 Flash，只有不一致且系统处于安全停止状态才修改。
3. 修改 PID 或执行 `$flash_reset#` 后，等待板卡重启并重新跑 `LINK_PROBE`。
4. 先使用 MTEP 做方向、符号和脉冲周期验证，再使用 MSPD 做速度换算验证，最后才使用 MAll 做累计里程。
5. 编码器数据必须带采样时间；不要把 10 ms 数据直接当作 RTOS 任务周期。

### 阶段 E：运动控制和故障恢复

- 速度闭环只允许对 `mtype=1/2/3` 的带编码器电机启用。
- `mtype=4` 只允许 PWM，必须配置独立的速度限幅和斜坡，不能假设板卡有闭环。
- 失去反馈、串口超时、字段错误、供电异常或状态不一致时，进入本地停止策略。
- 恢复时先停止、再重新探测、再读回参数，禁止链路恢复后直接沿用旧速度。
- 急停路径不能依赖 S3 BLE 回调；S3/ App 只发送意图，STM32 决定是否允许执行。

## 8. 编码器、速度和车体运动学

### 8.1 反馈数据的含义

- `MTEP` / I2C `0x10..0x13`：板卡给出的 10 ms 相对脉冲，适合做增量速度和方向诊断。
- `MAll` / I2C `0x20..0x27`：32 位累计脉冲，适合里程累计，但要处理回绕和掉电行为。
- `MSPD`：板卡根据线数、减速比、轮径等参数计算出的速度文本；单位在平台资料中写成 mm/s，控制指令 PDF 的单位描述不完整，必须实测校准。

### 8.2 推荐的实测校准

1. 轮子离地，给单个电机固定低速命令，记录 10 s 的 MTEP 和实际转数。
2. 验证正向命令产生正脉冲、反向产生负脉冲；如果相反，先修正 A/B 线序或 `mtype`，不要在上层随意取反。
3. 由实际转数计算每转脉冲，和供应商“磁环线数/减速比”对照；记录板卡内部到底采用何种计数边沿。
4. 用卷尺测量轮径和有效滚动周长，比较 MSPD 与外部测量的误差。
5. 在四轮同步低速、原地旋转和直线行驶三种工况分别记录 M1-M4，建立轮间符号和比例矩阵。

### 8.3 车体映射注意

板卡只知道 M1-M4，不知道 LF/LR/RF/RR 的机械朝向。Smart_Car 需要单独维护：

```text
wheel_index -> board_channel -> motor_direction_sign -> encoder_sign -> geometry
```

禁止把“板卡负速度”直接等同于“车体后退”。安装方向、左右镜像、A/B 相位和轮胎接触
方向都可能改变符号。

## 9. 固件更新和版本管理

### 9.1 官方流程

官方资料《如何更新固件.pdf》给出的流程：

1. 使用 USB Type-C 将板卡连接电脑。
2. 打开附件中的 `FlyMcu`，点击搜索串口并选择板卡串口。
3. 选择固件文件 `3.程序源码/固件/FourWay_Motor_STM32.hex`；资料包的 `6.附件` 只含烧录工具、串口助手和日志，不含 HEX 文件。
4. 界面按资料图片设置：`115200`，DTR 低电平复位、RTS 高电平进入 BootLoader；勾选校验、编程后执行、编程到 FLASH 时写选项字节，使用资料指定的串口编程模式。
5. 点击开始编程，等待工具报告成功。
6. 拔插 Type-C 使板卡重启；官方资料描述为红灯常亮、绿灯约 3 秒闪 2 次表示成功。

### 9.2 工程要求

- 更新前保存旧固件、板卡参数、`$read_flash#` 返回和版本日期。
- 不要把旧订单和 2026.6.24 后资料混用；资料目录明确要求新订单使用“新资料”子目录。
- 固件烧录成功只证明烧录器完成写入，不能证明 UART、I2C、编码器、电机或车辆行为。
- Smart_Car 当前任务没有执行烧录，本文不提供硬件烧录验收结论。

## 10. 各平台示例的可复用部分与不可复制部分

| 示例 | 可复用 | 不可直接复制到 Smart_Car |
| --- | --- | --- |
| STM32 F1 USART | ASCII 命令、`$...#` 状态机、MAll/MTEP/MSPD 字段 | F1 的 USART2、NVIC、寄存器库、PA2/PA3 初始化；H7 要走 HAL/FreeRTOS 和独立资源 |
| STM32 F1 I2C | 地址 `0x26`、寄存器和大端整数 | PB10/PB11 软件 I2C、忙等待和裸机延时；不能绕过 H7 I2C4/LSM303 资源管理 |

| ESP32 I2C | 400 kHz、`0x26`、小端 float、大端 int16 | 示例 SDA/SCL 和 ESP-IDF 旧 I2C API；Smart_Car 需适配当前 IDF/总线所有权 |
| Arduino | 最直观的控制和读取函数 | UNO 串口烧录限制、SoftwareSerial/Arduino API |
| MSPM0 | 10 ms 定时器和小车状态切换示例 | TI SysConfig、驱动库和 GPIO 分配 |
| PICO2/RDK/树莓派/Jetson | Python 字段解析、负数符号扩展、设备节点处理 | Linux `/dev/ttyUSB*`、MicroPython `machine.I2C`、平台物理引脚 |

不能作为 Smart_Car 的安全控制周期。示例源码中还存在旧式字符串解析、无严格字段检查、
阻塞发送和动态内存等问题，必须在 H7 上重写。

## 12. 故障排查顺序

### 12.1 没有任何返回

1. 确认板卡确实上电，USB 串口没有被其他程序占用。
2. 确认波特率为 115200、8N1、无流控。
3. 确认 TX/RX 交叉、GND 共地、电平兼容。
4. 发送最短 `$read_vol#`，观察 TX 波形；再发送 `$read_flash#`。
5. 清空 RX 缓冲后重新发送，检查是否把 `#` 丢失或加了不可见字符。
6. 若 USB Type-C 可识别但外部 TTL 不通，分别检查 Type-C 转换芯片和板卡外部 UART 引脚。

### 12.2 配置返回 OK 但电机不转

1. 先发送 `$pwm:0,0,0,0#`，确认不是残留命令。
2. 检查电机电源、电流限流和接线；逻辑供电正常不代表电机电源正常。
3. 确认带编码器电机使用 `$spd`，无编码器 TT 使用 `$pwm`。
4. 检查死区是否过大，死区必须通过逐步实验确定。
5. 检查 M1-M4 选择是否与实际插口一致。
6. 检查正负号、A/B 相线序和 `mtype`，不要直接修改上层方向矩阵掩盖硬件错误。

### 12.3 速度闭环抖动或速度不准

1. 先停用上层 PID，只读取 MTEP/MAll。
2. 核对 `mline`、`mphase` 和轮径；最常见错误是把线数和减速比写反。
3. 核对 520 黑色双头线导致 A/B 交换的特殊说明。
4. 用外部测速比较 MSPD，确认单位和符号。
5. 只有在参数和方向正确后才调 `$mpid`；修改 PID 会让板卡重启并停止电机。

### 12.4 I2C NACK 或数据异常

1. 确认没有同时连接板卡串口。
2. 扫描 7 位地址 `0x26`，检查 HAL 是否误传 `0x26` 而不是 `0x4C`。
3. 检查 I2C4 是否被 LSM303 任务占用，是否有总线互斥。
4. 检查上拉、电平、SCL 频率和线长。
5. 用已知寄存器 `0x10` 或 `0x08` 做短读，再检查大端/小端转换。
6. 不要自行尝试未公开的 PID/Flash 寄存器；需要这些能力时切换到串口方案。
